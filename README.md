Поточний результат: створено початкову сторінку з інформацією про номери готельного комплексу.

1.2 Навчальний ReactJS-проєкт веб-сайту готельного комплексу.

Поточний результат: застосунок розділено на повторно використовувані React-компоненти. Реалізовано спільне компонування та навігацію, список і картки номерів, повторно використовуваний статус номера, секції інтерфейсу та макет підготовки бронювання.

Для запуску застосунку використовується команда:

```powershell

```

Після запуску застосунок доступний за адресою:

```text
http://localhost:5173/
```

## Запуск через Docker

Для запуску проєкту через Docker використовуються команди:

```powershell

docker compose run --rm web npm install
docker compose up
```

## Лабораторна робота 3.1

У межах лабораторної роботи 3.1 завершено реалізацію CRUD-сценарію для вебзастосунку готельного комплексу.

**Основна сутність:** бронювання номера готелю.

### Реалізовані можливості

- Створення нового бронювання номера (Create).
- Перегляд списку бронювань та детальної інформації про окреме бронювання (Read).
- Редагування даних наявного бронювання (Update).
- Видалення бронювання після підтвердження користувачем (Delete).
- Використання спільної форми для створення та редагування бронювань.
- Перевірка обов'язкових полів, дат заїзду та виїзду, кількості гостей і доступності номерів.
- Відображення повідомлень про помилки без втрати введених даних.
- Відображення повідомлень про успішне виконання операцій після переходу між сторінками.
- Пошук бронювань за даними гостя.
- Фільтрація бронювань за категорією номера.
- Сортування списку бронювань.
- Збереження параметрів пошуку, фільтрації та сортування в URL.
- Відображення окремих повідомлень для порожнього списку та відсутності результатів пошуку.

### Модель даних

Основною сутністю є бронювання, яке містить унікальний ідентифікатор, дані гостя, категорію номера, кількість гостей, дати заїзду та виїзду.

Для керування колекцією бронювань використовується `BookingsContext`. Він забезпечує спільний доступ до даних, створення, оновлення та видалення записів.

Зміни колекції виконуються без безпосередньої мутації попереднього стану. Дані зберігаються в `localStorage` під ключем `hotel-complex-bookings`.

### Карта маршрутів CRUD-сценарію

| Маршрут | Призначення |
|---|---|
| `/bookings` | Перегляд списку бронювань |
| `/bookings/new` | Створення нового бронювання |
| `/bookings/:bookingId` | Перегляд деталей бронювання |
| `/bookings/:bookingId/edit` | Редагування бронювання |

Після успішного створення або редагування користувач переходить до збереженого запису. Видалення здійснюється лише після підтвердження.

### Карта стану

Для керування даними використовується React Context API.

- `BookingsContext` — спільна колекція бронювань та CRUD-операції.
- Локальний стан форми — введені значення, результати валідації та повідомлення про помилки.
- Параметри URL — пошук, фільтрація та сортування списку.
- `localStorage` — збереження колекції бронювань між перезавантаженнями сторінки.

Після успішного виконання CRUD-операції дані спільної колекції оновлюються, а інтерфейс відображає актуальний результат. У разі помилки введені значення форми зберігаються.

### Перевірка роботи

Для перевірки реалізованого CRUD-сценарію передбачено такі дії:

1. Створити бронювання з коректними даними.
2. Перевірити відображення створеного бронювання.
3. Відредагувати дані бронювання та перевірити збереження змін.
4. Спробувати надіслати форму з некоректними даними та перевірити повідомлення про помилки.
5. Перевірити пошук, фільтрацію та сортування списку.
6. Перевірити збереження параметрів списку в URL.
7. Видалити бронювання після підтвердження.
8. Оновити сторінку та перевірити збереження актуальних даних у `localStorage`.

Таким чином, у лабораторній роботі 3.1 реалізовано завершений CRUD-сценарій керування бронюваннями номерів готельного комплексу.

## Лабораторна робота 3.2. Асинхронна робота з даними та адаптери

### Мета роботи

Реалізувати асинхронну взаємодію вебзастосунку з джерелом даних через адаптер, забезпечити обробку станів завантаження та помилок, повторне виконання операцій і захист від застарілих відповідей.

### Опис проєкту

**Назва:** Вебсайт готельного комплексу.

**Основна сутність:** бронювання номера.

Робота продовжує лабораторну 3.1, у якій реалізовано створення, перегляд, редагування, видалення, пошук, фільтрацію та сортування бронювань.

### Архітектура роботи з даними

Для відокремлення інтерфейсу від джерела даних використано адаптери.

- `mockBookingsAdapter.js` — локальний адаптер, який імітує асинхронні операції та зберігає дані в `localStorage`.
- `bookingsAdapter.js` — модуль вибору адаптера.
- `BookingsContext.jsx` — провайдер підтверджених даних бронювань і операцій над ними.

Основний працездатний режим — **mock**. Підготовлений API-адаптер призначений для підключення сумісного серверного сервісу; фактична інтеграція з сервером у межах проведених перевірок не підтверджувалася.

### Контракт операцій

| Метод | Призначення |
|---|---|
| `getAll()` | Отримання всіх бронювань |
| `getById(id)` | Отримання бронювання за ідентифікатором |
| `create(data)` | Створення нового бронювання |
| `update(id, data)` | Оновлення наявного бронювання |
| `delete(id)` | Видалення бронювання |

Ідентифікатор бронювання зберігається в полі `id`. Для нових записів використовується UUID. Під час редагування ідентифікатор залишається незмінним.

Джерелом даних у mock-режимі є `localStorage`, колекція в `BookingsContext` є підтвердженим знімком, а введені користувачем значення у формі — локальною чернеткою.

### Асинхронні стани та захист

Реалізовано:

- стан завантаження `loading`;
- відображення помилок `error`;
- повторне читання через `retry()`;
- оновлення колекції після підтвердження операції адаптером;
- послідовне виконання операцій запису;
- блокування повторного подання форми;
- збереження введених значень після відмови;
- захист від застарілих відповідей за допомогою версій запитів.

Сторінки деталей і редагування не показують повідомлення про відсутній запис до завершення завантаження.

### Дослід getById

Для перевірки асинхронного читання за ідентифікатором створено тестовий компонент `GetByIdTest.jsx`.

Під час досліду використовувалися два різні бронювання. Першому запиту задано затримку 3000 мс, другому — 700 мс. Після швидкого перемикання між записами відображався результат останнього вибраного запиту. Застаріла відповідь не змінювала актуальне відображення.

Основні сторінки деталей використовують підтверджену колекцію провайдера, а не незалежну копію запису.

### Перевірка роботи

Під час ручного тестування перевірено:

1. Завантаження колекції бронювань.
2. Одноразову помилку `getAll` і повторне завантаження.
3. Створення, редагування та видалення бронювання.
4. Імітацію відмов `create`, `update` і `delete`.
5. Збереження введених даних після помилки.
6. Захист від застарілих відповідей `getById`.
7. Збереження порожньої колекції після перезавантаження.
8. Розрізнення порожнього списку та відсутності результатів фільтрації.
9. Збереження створеного бронювання після перезавантаження сторінки.

### Обмеження

Зберігання даних у mock-режимі обмежене поточним браузером і origin. Реальний серверний API не використовувався. Розширене автоматизоване тестування передбачено наступними лабораторними роботами.
